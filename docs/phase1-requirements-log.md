## Round 1 · 2026-09-07

### D1-1 计时模式：正计时 + 番茄钟并存，默认正计时

**决策**：两种模式都做，默认正计时。
**与建议的差异**：我推荐"MVP 只做正计时，番茄留 P1"。你选择了并存。

**影响**：
- `FocusSession` 需要增加 `mode` 字段（`STOPWATCH` / `POMODORO`）。
- 番茄模式需要额外的周期状态（专注中 / 休息中 / 第 N 个）。
- 计时状态机从 3 态（IDLE/RUNNING/PAUSED）扩展到约 6 态。

**复杂度评估**：**中等，可接受**。前提是采用我建议的最小实现——

> 番茄模式的 MVP 实现 = 「预设时长（25/45/50 分钟）+ 到点提醒 + 手动决定是否继续」，
> **不做**自动进入休息、**不做**自动开始下一个、**不做**强制锁定。

这样番茄本质上是"带目标时长的正计时"，状态机可以复用，只多一个 `targetDurationMs` 字段和一个到点通知。自动循环休息留到 P2。

**代价**：多约 1 个字段、1 个通知通道、1 套预设 UI。可接受。
**风险**：如果后续要求"番茄必须完整走完才算一个"，会产生"中断的番茄算不算"的数据歧义。需在第 2 轮确认。

### D1-2 消费与项目：可选关联

**决策**：`Expense` 上有可选的 `projectId`，默认不选，需要时手动挂。
**影响**：
- 数据模型：`Expense.projectId: Long?`（可空外键）。
- 解锁能力：「考研总投入 = 128h32m + ¥680」——时间与金钱可以在项目维度合并，这是差异化的真正落点。
- 记账主流程不增加任何必填步骤，摩擦不变。
**风险**：低。需要在记账 UI 上把"关联项目"做成次级操作（折叠区），不能挡住主流程。

---

### D1-3 不做 Todo / 待办

**决策**：不纳入任务层。产品只记录已经发生的事。
**影响**：
- 数据模型砍掉 `Task` 实体，砍掉任务状态机、截止日、提醒调度。
- 与 TickTick / Todoist / 番茄ToDo 正式划清边界：**我们是"回顾工具"，不是"规划工具"**。
- 用户故事里"开始学习→选项目→计时"这条主路径完全不受影响。
**风险**：产品会显得"不够全能"。这是主动取舍，接受。

---

### D1-4 数据策略：纯本地 + 手动导出

**决策**：无网络权限。Room 本地库 + 一键导出。
**影响**：
- `AndroidManifest` 不声明 `INTERNET` 权限——这是可以在设置页里向用户炫耀的事。
- 架构：单层数据源（Room），无 Repository 的远程分支，**无冲突解决问题**。
- 必须做：导出（JSON 全量 + CSV 明细）与导入。这是换机的唯一通道，属于 P0 而不是 P1——因为**没有导出 = 数据没有退路**。
**风险**：换机 / 手机丢失 = 数据丢失。需要你接受，并养成定期导出习惯。（可用 WorkManager 做"本地定期备份到 Download 目录"缓解，不需要网络权限。）

---

### D1-5 目标层：只要目标时长，不要预算

**决策**：项目可设目标时长并显示进度；金钱侧不做预算。
**影响**：
- `Project` 增加 `dailyTargetMinutes` / `weeklyTargetMinutes`（可空）。
- 首页可以显示"今日目标完成度"，这是考研场景的正反馈来源。
- 砍掉预算模块、超支提醒、预算周期计算。
**风险**：低。目标是"软提示"，不做惩罚机制（不弹超支警告）。

## Round 2 · 2026-09-07

### D2-1 异常会话：标记为「待确认」，人工修正

**决策**：超长/跨天未结束的会话不自动篡改，标记为待确认，用户手动确认时长或丢弃。
**影响**：
- `FocusSession` 增加 `status` 枚举：`RUNNING / COMPLETED / PENDING_REVIEW / DISCARDED`。
- 需要一个「待处理」入口（首页顶部卡片 / 设置页）。
- **必须实现进程恢复机制**：App 冷启动时检查是否存在 `status = RUNNING` 的会话，若有则接管并继续按时间戳计算（不丢数据，也不假装它还在跑）。
- 判定规则（初稿，可调）：持续 > 8 小时，或跨越超过 1 个日切时刻 → 标为 `PENDING_REVIEW`。
**复杂度**：中等，但**不可省**。这是「数据正确性」优先级的直接体现。

### D2-2 时间轴：只显示已记录的事件

**决策**：时间轴仅由 `FocusSession`（专注时段）与 `Expense`（消费时点）组成，不引入第三个事件实体。
**影响**：
- **时间轴不是一张表，而是一次查询时的合并排序**。运行时按 `timestamp` 把两个来源合并成 `TimelineItem` 密封类交给 UI。
- 数据模型保持两个事实来源，无冗余。
- 「空白就是没记录」——不做 24 小时填满，避免未记录时段制造噪音。
**风险**：一天的"时间覆盖率"无法统计（不知道有多少时间没被记录）。这是主动接受的代价。

### D2-3 消费分类：预置一套 + 可增删改

**决策**：预置餐饮 / 交通 / 购物 / 娱乐 / 学习 / 医疗 / 其他，用户可增删改、可换色换图标。
**影响**：
- `Category` 实体 + 首次启动 seed 数据；`isPreset` 标记区分预置与自建（预置的可禁用，不一定可删）。
- `Category` 与 `Project` **分开存**，不共用。理由：语义完全不同，共用会让「考研数学」出现在早餐的下拉框里。
- 「双账本对称」体现在**统计表达对称**（都有周期汇总 / 趋势 / 占比），而不是数据结构共用。

### D2-4 项目可归档

**决策**：项目可归档，归档后不在计时列表出现，历史与统计全部保留，可恢复。
**影响**：
- `Project` 增加 `isArchived`（或 `archivedAt`）。
- 所有统计查询默认包含已归档项目（否则考研结束一归档，历史数据就"消失"了）。
- 计时选择器只查 `isArchived = false`。
- 这条直接回应了"考完研之后怎么办"——**归档让 App 能从阶段性工具平滑过渡到长期记录工具**。

### D2-5 跨午夜：归属开始日 + 可配置日切时刻（默认 04:00）

**决策**：会话归属到它的**开始日**；「一天」的起点可配置，默认凌晨 4 点。
**影响（这是最重要的架构约束之一）**：
- 全 App **禁止**直接用 `LocalDate.now()` 或 `date('now')` 判断"今天"。
- 必须有统一的日期换算工具（如 `DayBoundary`），把时间戳 → 业务日期：`businessDate(ts) = (ts - dayStartHour) 的日期`。
- 所有"今日/本周/本月/本年"统计与所有 Room SQL 查询，都必须经过这个换算。
- 「本周」起点（周一 or 周日）同样需要可配置，默认周一。
- 导出数据时需一并写入日切配置，否则换机后历史统计口径会漂移。
**风险**：这是最容易埋 bug 的地方。列为架构级约束，单元测试必须覆盖：23:59 起始、00:30 起始、跨日切、跨月、跨年。

## 由 Round 1 + Round 2 推导出的架构硬约束

1. **单一事实来源**：`FocusSession` 与 `Expense` 是仅有的两张事实表；所有统计通过查询计算，不落冗余汇总表（MVP 阶段）。
2. **统一日期边界**：所有时间聚合走 `DayBoundary` 工具，禁止裸用系统日期。
3. **时间轴是查询结果的合并投影**，不是存储实体。
4. **会话状态机**：`IDLE → RUNNING ⇄ PAUSED → COMPLETED`，异常分支进 `PENDING_REVIEW`。
5. **不声明 `INTERNET` 权限**；导出/导入为 P0。
6. **进程可恢复**：冷启动接管 `RUNNING` 会话，用时间戳而非 UI 累加计算时长。

## Round 3 · 2026-09-07

### D3-1 定位：长期生活记录工具，不是考研专用工具

**决策**：考研只是第一个项目，考完会继续用于工作、健身、阅读、编程。
**影响**：
- 项目归档、长期累计、导出/导入**全部从"可选"升级为"必须"**。
- 数据结构不允许写死任何"考研"语义（分类、项目名全部用户自定义）。
- 跨年度统计必须可用（"2026 全年"），不能只做年内视图。
- 反面：不为考研做特化功能（倒计时、考试日程等）——那是计划层，已排除。

### D3-2 收入：MVP 只记支出，但预留字段

**决策**：界面只做支出，数据库预留 `type` 字段（有默认值，非 null）。
**影响**：`Expense.type` 默认 `"EXPENSE"`。未来加收入是纯 UI 工作，**零数据迁移**。
**成本**：约等于零。**收益**：避免一次 Room Migration。

### D3-3 快速入口：通知栏常驻 + 桌面小组件，都进 MVP

**决策**：两者都做。
**影响**：
- 计时必须跑在 **Foreground Service** 并展示常驻通知——这是 Android 后台存活的**强制要求**，不是可选项。
- 桌面小组件用 **Jetpack Glance**（Compose 风格 API，与整体技术栈一致）。
- 小组件承载两个动作：一键开始/结束当前项目计时、一键唤起记账页。
**风险**：Glance 有独立的渲染限制（不支持全部 Compose API），小组件 UI 需单独设计，不能复用 App 内组件。

### D3-4 首屏：四个要素全要

**决策**：当前计时卡片 + 三个数字 + 目标进度 + 快捷按钮 + 昨日对比，全部保留。
**影响**：首屏信息密度高，**必须靠信息层级而不是靠删减来控制**：

```
① 当前计时卡片（有则置顶，无则整块消失，不留空白）
② 三个大数字 + 昨日对比（小字灰色，附在数字下方）
③ 今日目标进度条
④ 两个主按钮：记一笔 / 开始计时
⑤ 今日时间轴（可滚动，承接下方）
```

> **2026-09-07 修正（用户验证）**：⑤ 时间轴**只呈现 FocusSession，不含 Expense**。
> 用户原话：消费的发生时刻对他没有意义。→ PRD 原则 2 与 US-11 已同步修正。

---

### D3-5 时间轴：不含消费条目（用户验证推翻原设计）

**决策**：时间轴只投影 `FocusSession`。消费以"周期总额 + 分类占比 + 趋势"呈现，不进入时间轴。
**影响**：
- `TimelineItem` 不再是合并投影，退化为 FocusSession 的视图模型。
- 首页时间轴查询简化为单表查询。
- **双账本的融合点收敛为：项目维度的时间与金钱合并**（考研数学 128h32m + ¥680）。
**风险**：PRD 中的 R1 风险提前触发（原定 30 天后验证，用户直接给了结论）。这是好事——省了一个月的错误投入。
**连带判断**：「消费可选挂项目」的入口只剩项目详情页，**价值未验证，降为 P1**（UI 不做，字段照留）。

**一个口径问题（已定）**：「与昨日对比」天然不公平。
晚上 21 点打开，今日 6h40m 对比昨日**全天** 8h20m，永远是下降的。
**既定口径**：对比「昨日同一时刻为止的累计值」（昨日 00:00–21:00），并在有效数据不足 7 天时隐藏该模块，显示"数据积累中"。
