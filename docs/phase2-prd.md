## 1. 产品定位

### 1.1 一句话定义

> **DailySchedule 是一个 Local-first 的个人「双账本」记录工具。它用同一条时间轴回答同一个问题：我今天的时间和钱，到底花在哪里了。**

### 1.2 定位三原则

| # | 原则 | 含义 |
| --- | --- | --- |
| 1 | **记录已发生的，不规划未发生的** | 不做 Todo、不做日历、不做排程。产品站在"回顾"这一侧 |
| 2 | **同一屏看见时间账与金钱账** | 两个账本共享同一套周期统计、同一套项目维度、同一套视觉语言 |
| 3 | **数据属于用户** | 不登录、不上传、不声明网络权限，永远可完整导出 |

> **已修正（2026-09-07）**：原原则 2 写作"时间账与金钱账在同一条时间轴上"，经用户验证**不成立**——消费的"发生时刻"对他没有回顾价值。
> 修正后：**时间轴只呈现专注时段**。金钱账以"周期总额 + 分类占比 + 趋势"呈现，不进入时间轴。
> 双账本的融合点因此收敛为：**项目维度的时间与金钱合并**（考研数学 128h32m + ¥680）。

### 1.3 明确不是什么（Non-goals）

- **不是记账 App**：不做复式记账、多账户、转账、银行同步、投资资产、共享账本。
- **不是任务管理器**：不做任务、截止日、提醒、优先级、看板。
- **不是专注训练工具**：不做锁机、应用拦截、游戏化、自习室、排行榜。
- **不是计划工具**：不做日历排程、时间块规划。

> 这四条必须写死。任何新需求先对照这四条，违反即拒绝。

## 2. 目标用户

### 2.1 主要用户（唯一真实用户）

| 维度 | 描述 |
| --- | --- |
| 身份 | 考研备考学生，Android 用户 |
| 设备 | 单台 Android 手机 |
| 核心动机 | 知道自己每天在考研各科上投入了多少时间、花了多少钱 |
| 使用周期 | 考研只是起点，考完继续用于工作 / 健身 / 阅读 / 编程（D3-1） |
| 技术水平 | 具备软件工程背景，重视架构与数据正确性 |
| 隐私偏好 | 强。财务与生活轨迹数据不接受上传 |

### 2.2 诚实的风险说明

**目标用户只有一个人，是这个项目最大的优势，也是最大的风险。**

- 优势：不需要做用户调研妥协、不需要增长、不需要付费墙、不需要兼容低端机型与多语言。
- 风险：缺少外部反馈回路，容易做出"自己觉得合理但很难用"的东西。
- 缓解：**MVP 阶段用真实数据自测 30 天**，用"30 天留存 + 单笔记录耗时"作为客观指标，而不是靠主观感觉。

## 3. 核心使用场景

| # | 场景 | 触发时机 | 期望结果 |
| --- | --- | --- | --- |
| S1 | **开始学习计时** | 坐下来准备学数学 | 选项目 → 点开始 → 手机锁屏放一边，计时继续 |
| S2 | **结束/暂停计时** | 学完一章，或去吃饭 | 点结束，时长自动计入项目；中间可暂停 |
| S3 | **随手记一笔** | 买完早餐，手还腾得出 | 一次点击打开 → 输金额 → 点分类 → 完成（< 5 秒） |
| S4 | **晚上回顾今天** | 睡前打开 App | 一屏看到"我今天做了什么、花了多少" |
| S5 | **查看项目累计** | 想确认数学到底投入了多少 | 看到 今日 / 本周 / 本月 / 累计 四个数字 |
| S6 | **周/月末看趋势** | 周日晚上或月末 | 看到学习时长与消费的趋势与变化 |
| S7 | **处理忘记结束的计时** | 第二天打开 App | 看到"待确认"卡片，补上正确时长或丢弃 |
| S8 | **换机 / 备份** | 换手机前 | 一键导出文件，新机导入，历史完整保留 |

## 4. 用户故事

### 4.1 时间账

- **US-01** 作为考研学生，我希望在学习考研数学时点一下就能开始计时，从而知道自己每天在数学上投入了多少时间。
- **US-02** 作为用户，我希望在去吃饭时暂停计时、回来继续，从而不让"吃饭时间"被算进学习时间。
- **US-03** 作为用户，我希望在忘记点结束时能事后补录/修正这段时长，从而不因为一次疏忽毁掉一整天的数据。
- **US-04** 作为用户，我希望看到"考研数学：今日 2h35m / 本周 8h40m / 本月 31h20m / 累计 128h32m"，从而判断自己的投入是否足够。
- **US-05** 作为经常熬夜的用户，我希望凌晨 1 点结束的学习算作"当天"，从而统计数据符合我的真实作息。
- **US-06** 作为用户，我希望项目可以设置每日目标时长并看到进度，从而获得持续的正反馈。

### 4.2 金钱账

- **US-07** 作为用户，我希望买完东西后能在 5 秒内记完一笔，从而不会因为嫌麻烦而放弃记账。
- **US-08** 作为用户，我希望给某笔消费挂到某个项目上（如"考研数学-习题册 ¥68"），从而知道考研这件事总共花了我多少钱。
- **US-09** 作为用户，我希望看到今日 / 本周 / 本月 / 本年的消费总额与分类占比，从而知道钱主要花在哪。
- **US-10** 作为用户，我希望消费分类可以自己增删改，从而让分类符合我的真实生活。

### 4.3 融合与回顾

- **US-11** 作为用户，我希望晚上打开 App 就能看到今天的学习时段按顺序排成一条时间轴，从而回答"我今天到底做了什么"。
- **US-12** 作为用户，我希望在同一屏同时看到"今日学习时长"和"今日消费金额"，从而直观感受时间与钱的去向。
- **US-12a**（已证伪并移除）~~我希望消费条目出现在时间轴上~~ → 用户验证：**消费的发生时刻无回顾价值，不进时间轴。**

### 4.4 数据与隐私

- **US-13** 作为注重隐私的用户，我希望 App 完全离线运行、不申请网络权限，从而不用担心数据被上传。
- **US-14** 作为用户，我希望换手机时能一键导出全部数据并在新机导入，从而不丢失几年的记录。
- **US-15** 作为用户，我希望手机重启或 App 被系统杀掉后，正在进行的计时依然正确，从而信任这个 App 的数据。

## 6. MVP 范围（Phase 7 交付物）

MVP = **P0 全部 + 无任何 P1**。

**四个 Tab**：

```
今日  ·  统计  ·  记录  ·  项目
```

| Tab | 内容 |
| --- | --- |
| **今日** | 三数字 + 昨日同刻对比 · 当前计时卡片 · 目标进度 · 记一笔/开始计时 · 今日时间轴（仅专注时段） |
| **统计** | 周期切换（日/周/月/年）· 学习时长汇总 · 消费金额汇总 · 项目排行 |
| **记录** | 计时页（选项目 → 开始）· 记账页（金额 → 分类 → 完成） |
| **项目** | 项目列表 · 新建/编辑 · 点击进项目详情（四级累计 + 关联消费） |

**MVP 明确不做**：图表（P1）、搜索筛选（P1）、归档（P1）、深色模式（P1）、收入（P2）、预算（P2）。

> 图表放 P1 是有意的：**先保证数字是对的，再让数字好看。** 统计页 MVP 阶段用数字 + 简单进度条呈现即可。

## 7. 非功能需求

### 7.1 优先级顺序（不可颠倒）

```
稳定性  >  数据正确性  >  操作效率  >  功能数量
```

### 7.2 具体指标

| 类别 | 指标 |
| --- | --- |
| **计时正确性** | 后台 / 锁屏 / 进程被杀 / 手机重启，四种情况下累计误差 **< 1 秒** |
| **计时实现** | 基于 `SystemClock.elapsedRealtime()` 的绝对时间戳，**禁止** UI 每秒累加 |
| **数据正确性** | 系统**永不**自动修改或截断用户会话；异常数据只标记、不篡改 |
| **进程恢复** | 任意时刻冷启动，正在进行的会话继续正确显示 |
| **崩溃恢复** | 任何写操作在事务内；单次写入失败不产生半条记录 |
| **记录效率** | 记一笔消费：从点击图标到保存完成 **< 5 秒** |
| **启动效率** | 冷启动到首屏可交互 **< 1.5 秒** |
| **存储** | 不声明 `INTERNET` 权限；导出文件写入用户可见目录 |
| **数据可移植** | 导出的 JSON 必须包含全部业务数据与配置（含日切时刻） |
| **最低版本** | Android 8.0（API 26）起步，targetSdk 用当前稳定版 |

### 7.3 必须处理的边界情况（清单）

| 场景 | 要求 |
| --- | --- |
| App 进入后台 / 锁屏 | 计时继续，通知常驻 |
| 系统杀死进程 | 重启后从 DB 恢复会话，按时间戳补算时长 |
| 手机重启 | 同上；提供"检测到未完成会话"提示 |
| 跨午夜（日切 04:00） | 会话归属开始日；03:30 结束算前一天 |
| 时区变化 | 全部时间以 epoch millis 存储，展示时才转本地时区 |
| 系统时间被改 | 用 `elapsedRealtime`（单调时钟）计算时长，不受影响 |
| 日期边界（月末 / 年末） | 周/月/年聚合必须覆盖跨月跨年，单测覆盖 |
| 导出时数据量大 | 分批写入，主线程不阻塞 |
| 导入冲突 | 提供"覆盖"与"合并"两种模式，导入前自动备份 |

## 8. 关键流程

### 8.1 主流程：开始一次学习计时

```
小组件 或 首页「开始计时」
   → 选项目（默认上次使用的项目，可一键确认）
   → 点开始
   → 写 FocusSession(status=RUNNING, startElapsed, startWallClock, projectId)
   → 启动 Foreground Service + 常驻通知
   → 锁屏 / 切走，计时继续
   → 点结束 → status=COMPLETED, endElapsed → 计算 durationMs
   → 首页数字与时间轴即时刷新
```

### 8.2 异常流程：忘记结束

```
App 冷启动 / 定时检查
   → 发现 status=RUNNING 且 (now - startElapsed) > 阈值(8h 或跨越 1 个日切)
   → 保持 RUNNING，但在首页顶部插入「待确认」卡片
   → 用户操作：
       · 填写真实结束时间 → status=COMPLETED
       · 直接丢弃         → status=DISCARDED（软删除，不物理删）
       · 忽略             → 继续计时
```

### 8.3 主流程：记一笔

```
小组件 或 首页「记一笔」
   → 数字键盘（默认聚焦，可直接输入金额）
   → 点分类（九宫格，一次点击）
   → 可选：备注 / 改时间 / 挂项目（折叠区，不阻断主流程）
   → 自动保存并退出（**不需要点"保存"**）
```

> 关键：**取消"保存"按钮**。选完分类即落库。想改再进编辑页。这是把 7 次点击压到 3 次的核心手段。

## 9. 数据模型预览（Phase 4 细化）

| 实体 | 关键字段 | 说明 |
| --- | --- | --- |
| **Project** | `id, name, icon, colorHex, isArchived, dailyTargetMinutes, sortOrder, createdAt` | 时间账的分类维度，也是消费的可选归属 |
| **FocusSession** | `id, projectId, status, startElapsedMs, startWallClockMs, endElapsedMs, accumulatedPauseMs, mode, targetDurationMs, note, createdAt` | **唯一的时间事实来源** |
| **Expense** | `id, amountCents, categoryId, projectId?, type, note, occurredAt, createdAt` | **唯一的金钱事实来源**；金额用"分"存整数 |
| **Category** | `id, name, icon, colorHex, isPreset, isEnabled, sortOrder` | 消费分类，与 Project 分开存 |
| **UserPreference** | `dayStartHour, weekStartDay, lastUsedProjectId, ...` | DataStore 存储 |

**设计原则**：

1. **只有两张事实表**：`FocusSession` 与 `Expense`。所有统计通过查询计算，**不落冗余汇总表**。
2. **时间轴不是表**：运行时把 `FocusSession` 投影为 `TimelineItem`，不额外存储。**（已修正：Expense 不参与时间轴投影）**
3. **双时钟**：`elapsedRealtime`（算时长，不受系统改时间影响）+ `wallClockMillis`（算归属日期，用于展示）。
4. **软删除**：`DISCARDED` 状态而非物理删除，便于审计与误操作恢复。
5. **金额用整数分**：避免浮点误差。

## 10. 成功标准（如何判断 MVP 成功）

| 指标 | 目标 | 测量方式 |
| --- | --- | --- |
| **留存** | 连续 30 天，每天至少 1 条记录（计时或消费） | 自查数据库 |
| **记录效率** | 记一笔 ≤ 5 秒；开始计时 ≤ 3 秒 | 手动计时实测 10 次取中位 |
| **数据完整性** | 30 天内 0 次数据丢失；异常会话全部被正确处理 | 日志 + 自查 |
| **计时准确性** | 与手机秒表对照，1 小时误差 < 1 秒 | 手动对照测试 |
| **崩溃率** | 30 天内 0 次用户可感知崩溃 | 使用观察 |
| **主观标准** | 晚上愿意打开 App 回看今天 | 主观，但这是真正的成功标准 |

> 最后一条最重要。如果这个 App 你晚上不想打开，前面五条都没意义。

## 11. 风险与待定

| # | 风险 / 待定项 | 处理 |
| --- | --- | --- |
| R1 | ~~「同一条时间轴上的两个账本」是否真有新价值~~ → **已验证：不成立（2026-09-07）** | 用户明确表示消费的时刻无意义。已砍掉时间轴中的消费条目。双账本融合点收敛为**项目维度的时间 + 金钱合并**。剩余价值待 30 天真实数据二次检验：若"考研花了多少钱"也从未被查看，则项目关联降为 P2 |

| R3 | 纯本地 + 手动导出，换机/丢手机即丢失数据 | 已接受。缓解：P1 增加 WorkManager 定期本地备份 |
| R4 | 番茄模式与正计时并存，可能产生"中断的番茄算不算"歧义 | 既定口径：番茄只作为"带目标时长的正计时"，不统计"番茄个数" |
| R5 | Glance 小组件 API 受限，UI 需单独实现 | 小组件只做最小 UI：当前项目名 + 时长 + 开始/结束按钮 |
| R6 | 与昨日对比在早期数据不足时无意义 | 有效数据 < 7 天时隐藏该模块 |
| R7 | 首屏信息密度高（4 个要素全要） | 靠信息层级控制；若真机测试发现拥挤，优先降级「昨日对比」 |
