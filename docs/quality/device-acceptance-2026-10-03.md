## 关键证据

### 导出文件与设备库逐字段比对

验收脚本不做「JSON 自洽」这种弱断言 —— 自洽只能证明文件内部没矛盾，证明不了文件与库一致。
脚本会先 `am force-stop` 让 WAL 落盘，再把 `databases/dailyschedule.db` 拉下来，
用 SQLite 打开后按 id 逐字段与 JSON 对比：

```
projects   JSON 1 条，与库逐 id 逐字段一致
categories JSON 7 条，与库逐 id 逐字段一致
sessions   JSON 5 条，与库逐 id 逐字段一致
expenses   JSON 2 条，与库逐 id 逐字段一致
```

### 补录记录落库后的字段

```
id=5  projectId=1  COMPLETED  MANUAL  STOPWATCH
      durationMs=2700000   endWallClockMs - startWallClockMs = 2700000   （相等）
```

补录记录满足 `end - start == durationMs` —— 这是设计里明确要求的：补录的两个时间戳
是事后按「多久 + 哪一天」造出来的，如果不满足这个不变量，设置页的「数据体检」
会把正常补录误报成数据不一致。（对照：纯计时记录满足的是
`end - start - accumulatedPauseMs == durationMs`，如 id=2 的 59306 − 802 = 58504。）

## 本轮修掉的缺陷：全部在验收脚本自身

应用没查出问题，倒是验收脚本本身有四处问题，都会让**结论失真**，一并修了：

| # | 问题 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | `center_of` 从整行里取第一个 `bounds` | uiautomator 把整棵层级树输出成**一行**（`wc -l` 为 0），所以每次取到的都是根节点的全屏 bounds，点出去是屏幕正中央 `(610,1356)` 而不是设置图标 `(1129,242)`。所有点击静默落空。 | 先按 `<node` 切块，再取该块自己的 bounds |
| 2 | `has()` 把 `$1` 同时当模式与文件名 | 断言永远读不到正确的 dump 文件，全部返回假阴性 —— 实际导出成功了却报「没有回报导出成功」 | 改为 `grep -q "$1" "ui_$2.xml"` |
| 3 | 结论行只看内容校验的返回值 | 第 7、8 步全失败，结尾仍打印「✅ 结论：导出与导入路径走通」——**假阳性** | 改用失败计数器，有任何一项失败即非零退出 |
| 4 | 导入路径没有真正走到选文件 | 选择器「最近」标签只索引媒体文件，JSON 不在其中；按来源搜出的「传输与下载」走的是索引，同样漏掉刚生成的 JSON | 走「浏览 → Download」，用**慢速**滑动翻页（快甩会被判成对某行的点击），并对被吸顶面包屑盖住的首行做小步下拖 |

判定文件选择器里那一步的坐标时还踩到一个坑值得记：被吸顶面包屑遮住的行**仍在无障碍树里**，
坐标看着有效但点不到。所以定位时要带纵坐标范围，或先把该行拖出来。
